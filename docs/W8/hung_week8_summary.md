host. It is **not** cloud staging evidence — DV-HUNG-06 still needs one run
against the private cloud host.

Three defects were found only by running it, and are fixed: the proxy crash-looped

repository had a `.gitattributes`.

## 4. Action required from the team

### 4.1 P0 — staging currently deploys an unauthenticated UI · owner: Duy

`deployment/cloud/docker-compose.staging.yml` publishes Streamlit directly on the
host with no proxy and no authentication, and `deploy-staging.yml` records that
address as the staging Environment URL. Streamlit authenticates nothing, so every
uploaded document, prediction, RAG answer and report would be readable by anyone
who reaches the port. This fails the DV-HUNG-07 criterion *"absence of an
unauthenticated public Streamlit endpoint"* and release criterion *"private
staging access is protected"*.

> **Do not dispatch `deploy-staging.yml` and do not share a staging URL until the
> changes in `hung_week8_canonical_staging_gap.md` §2 are merged.** If the
> pipeline has already been dispatched against a reachable host, treat the data
> loaded there as disclosed.

`deployment/cloud/docker-compose.staging-proxy.yml` closes it and is on the
branch. The proxy takes over the same published port, so `ui_url` and the cloud
acceptance check keep working unchanged. Four changes are still needed in
`deploy-staging.yml` and the staging Environment — listed with exact commands in
§2 of the gap document. TLS in front of the proxy remains open and is the last
control needed before any URL is shared.

### 4.2 Blocks DV-HUNG-06 — a contract field is missing · owner: Duy

`GET /api/ingestion/status` on the deployed backend returns no
`file_hash_sha256`, and no equivalent under any name. The agreed fixture
`demo/fixtures/week7/duy_latest_ingestion_summary.json` carries it and the
dashboard renders it as "File Hash (SHA-256)". Against the deployment the
dashboard therefore shows *"Not available in current data."* and the journey
refuses the run:

```text
AssertionError: Dashboard rendered placeholders instead of live ingestion values
```

That is the gate working — the assertion exists so a dashboard of placeholders
cannot be signed off as live data. Until the field is served, DV-HUNG-06 cannot
pass on any deployment, cloud or local.

### 4.3 Fails a first deployment onto a fresh volume · owner: Duy / Phat

The staging database healthcheck is `pg_isready -U ... -d ...` with no `-h`, so it
connects over the Unix socket, which Postgres accepts during initdb before it
listens on TCP. Compose reported `db Healthy`, `staging-seed` started and failed
with `connection to server at "db" ... Connection refused`. Re-running the
identical seed once Postgres was fully up succeeded with exit 0, confirming a
startup race, not a configuration error. It fails a **first** deployment and
passes on retry. Fix: `pg_isready -h 127.0.0.1 -U ... -d ...`.

### 4.4 Generated fixtures violate the UI contract · owner: Tường

`demo/fixtures/week7/tuong_prediction_batch_response.json` and
`tuong_prediction_review_queue_sample.json` on `main` carry a null
`document_external_id` and `prediction_log_id`. The UI fixture validator rejects
both, because they break the prediction → document → log trace the release
criteria rely on. The integration branch carries the contract-conformant set and
both sets keep `tests/ai_tests/test_ui_fixtures.py` green (18 passed), but
`scripts/week7_refresh_fixtures.py` will reintroduce the nulls. The fix belongs in
the payloads or the generator.

### 4.5 Cloud acceptance checks the UI with one liveness probe · owner: Duy

`week8_staging_smoke_test.py` reduces the whole UI to `"ok" in ui_health`, i.e.
`GET /_stcore/health`. Streamlit answers that even when every page raises, so the
15-check acceptance can report a green UI for a release in which nothing renders —
the same class of false green Week 8 was opened to remove, moved from fixture mode
to deployment. `scripts/week8_staging_acceptance.py` should become a required step
in `deploy-staging.yml` after the acceptance check.

## 6. What closes DV-HUNG-06 and DV-HUNG-07

Once §4.1 is merged and a staging URL exists, one command produces the whole
acceptance record, run from a machine inside `STAGING_ALLOWED_CIDRS` after
confirming a 403 from outside it:

```bash
export QS_E2E_HTTP_USER=reviewer
export QS_E2E_HTTP_PASSWORD=...          # never on the command line

python scripts/week8_staging_acceptance.py \
  --ui-url https://<staging-host> \
  --release-sha <exact release sha> \
  --allowlist-denied-verified
```

It performs the access-control checks and the browser journey and writes
`outputs/week8/hung_staging_acceptance.json` bound to one release SHA. The
allowlist check fails closed: without the attestation flag the run fails rather
than reporting an unverified control as green. The journey runs only after the
access controls hold, because a green journey against an unprotected UI is
evidence of the wrong thing.
